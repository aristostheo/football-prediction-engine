# Football predictor: independent repository review

Review date: 14 October 2026. Repository: `aristostheo/football-prediction-engine`.
Reviewed remote main: `e668d1e81ee5bddc348824acb89a9b368caee530`.
The existing checkout plus its already-published fixture-ribbon CSS change matched
that remote revision. This review changes no production code or data.

## Assessment

This is a credible personal-use and research MVP with a substantial functioning
backend, a distinctive dashboard, and reproducible probabilistic evaluation.
The historical model is meaningfully better than predicting league base rates.
The previous server-blocking prediction problem is substantially resolved.

It is not yet a reliable unattended service, and there is no demonstrated betting
advantage over the closing market. The most urgent problems are operational and
correctness problems: automatic data refresh is broken, every league's bundled
history stops at September 20, and live feature handling differs from historical
evaluation after long gaps. More UI features or a more elaborate model would not
resolve these problems.

Recommendation: retain the current architecture while repairing those problems,
establish an automated regression gate, and collect an honest prospective sample.
Revisit league-specific modelling only after the data and evaluation paths agree.

## How the production model works today

- Each league has its own historical stream and team states. Same-date fixtures
  use prior state before that date's results are applied.
- Elo starts at 1500, with K=20 and a 60-point home advantage. Result and opponent
  strength drive updates; goal margin is not used. Historical gaps over 180 days
  clear form and regress Elo toward 1500 with a 365-day half-life.
- Form uses five recent games with equal weights: points, goals for/against,
  venue-specific points, and capped rest days. There is no explicit exponential
  recency weighting in the production goal-model training likelihood.
- Separate regularised Poisson regressions estimate home and away goal rates.
  Their penalty is chosen through chronological cross-validation.
- Premier League 1X2 uses 25% Elo and 75% Poisson. The other six leagues use Elo
  for 1X2. All seven use the separate Poisson model for scorelines.
- Score distributions cover 0–12 goals and are normalised. They are independent
  Poisson, not Dixon–Coles. Their implied 1X2 need not equal the displayed Elo or
  ensemble forecast; the interface explains this distinction.
- Registered clubs without any history get Elo 1400 and a 50% mixture with league
  outcome priors. This is different from a returning club with old history.
- H2H is displayed as context. It does not change production 1X2 probabilities.
  Neither injuries, lineups, weather, shots nor xG is a production input.
- There is no explicit post-fit probability calibration transform. Odds are
  converted to margin-free probabilities for comparison and leave the independent
  model forecast intact.

The six Elo-only leagues can never select draw as the most probable outcome
with the current draw factor of 0.75. Their draw probabilities still have a
meaningful role in probability scoring; forcing more draw top picks would not
automatically improve probability quality.

## Findings in priority order

### 1. High: scheduled refresh is broken; live inputs are stale

Source: `.github/workflows/refresh-results.yml`.

Both visible scheduled runs failed:
[October 6](https://github.com/aristostheo/football-prediction-engine/actions/runs/37485887201)
and [October 13](https://github.com/aristostheo/football-prediction-engine/actions/runs/38427415627).
The October 13 job log explicitly says:

> Unable to resolve action `astral-sh/setup-uv@v10`, unable to find version `v10`

The job fails during setup, before downloading results. The manifest was generated
October 10, but **every league's latest stored result is September 20**, 24 days
before this review. A retrieval timestamp is not a results cutoff. Live fixtures
and journal settlement do not update team strength or retrain the goal model.

Change: repair the action reference using a verified released version/commit,
run the refresh, inspect actual new match counts, and alert on failure and stale
league cutoffs. If the upstream files remain behind, report that separately and
use a validated results adapter rather than treating a successful download as
freshness. Local users must pull the refreshed data and restart the server.

### 2. High: live and historical feature paths disagree after a long gap

Sources: `features.py::build_future_fixture_features`,
`features.py::_prepare_state_after_gap`, `prediction.py::_fixture_features`.

Historical feature construction applies the gap reset. Future feature construction
reads cached terminal states without applying that reset. Returning clubs and
long-unobserved teams can retain years-old form and ratings in the live path.

Reproduced real example, Sunderland–West Ham on 2025-08-16, using identical
pre-match historical rows:

| Item | Live engine | Historical benchmark |
| --- | ---: | ---: |
| Sunderland Elo | 1452.60 | 1499.84 |
| Form games | 5 | 0 |
| Home win | 24.32% | 32.97% |
| Draw | 24.87% | 26.57% |
| Away win | 50.81% | 40.46% |

The home-win difference is 8.65 percentage points. A second future-gap check
showed Arsenal retaining five form games in the live path when historical replay
cleared them. This is a correctness discrepancy, not evidence that one new model
is more accurate. It also means the benchmark helper is not a perfect serving-path
replica at these boundaries.

Change: construct future states through the same gap preparation, using copies so
one forecast cannot mutate another. Add live/historical parity tests for normal
fixtures, returning clubs, genuinely unseen clubs, gaps, and same-date fixtures.
Test the actual serving policy's promoted prior in historical replay too.

### 3. High: Greek history remains insufficiently complete

Sources: bundled CSV, manifest, `ingestion.py`, `docs/data-sources.md`.

Greek seasons have 240, 182, 182, 182, 182, 62 and 35 stored games for 2018-19,
2019-20, 2020-21, 2023-24, 2024-25, 2025-26 and 2026-27 respectively. Entire
2021-22 and 2022-23 seasons are absent, and 2025-26 is incomplete. Playoff stages
are excluded. Those missing fixtures cannot be repaired by an Elo reset alone.

The five additional leagues have much more continuous history. Greece's promising
earlier DC results do not justify deployment from two test seasons and gapped
training. Provider fixtures can also include stages outside the regular-season
training scope, without the dashboard identifying that modelling limitation.

Change: prioritise completed-result coverage and stage metadata for Greece before
trying injuries, xG, or a league-specific production replacement. Validate schedule
counts for each stage and make unsupported-stage handling explicit.

### 4. Medium: refresh can make later same-day fixtures unforecastable

Source: `prediction.py::predict`.

The engine rejects any fixture date on or before the latest stored result date,
even if its kickoff is later and still in the future. A controlled history ending
today rejected a kickoff at 23:59 today. This is a deliberate conservative leakage
guard, but it becomes a product problem when results are refreshed during a
matchday.

Change: use an explicit as-of snapshot. With date-only history, exclude all results
from the target day when preparing its forecast. Use within-day results only after
trusted kickoff/completion timestamps exist. Preserve rejection of forecasts
created after kickoff.

### 5. Medium: journal settlement has a 14-day blind spot

Sources: `api.py::scorecard_results`, dashboard journal refresh.

With the bundle missing a result, a fake provider settled a 14-day-old forecast,
but a 15-day-old forecast returned pending without contacting the same provider.
If the user does not open the journal promptly and the bundle is stale, a completed
game can stay unresolved indefinitely. Cached already-confirmed results help only
if settlement happened previously.

Change: permit bounded explicit backfill for unresolved forecasts, keep durable
confirmed settlements, and show whether pending means unfinished, unavailable,
outside the lookup window, or a provider failure. A game postponed to another date
also needs provider-ID/reschedule linkage; the current journal key is date/team
based and does not retain the provider fixture ID.

The current journal is useful for personal review. It replaces forecasts when
regenerated and lets users delete entries, so it is not an immutable prospective
research log. Records store policy/cutoff but not the dataset hash or model version.
CSV export also omits the stored market snapshot timestamp. Add those identities
before treating the journal as objective evidence of an edge.

### 6. Medium: provider caching can waste the daily quota

Sources: `api.py::get_cached_fixtures`, `_cached_team_badges`, `market_odds.py::_events`.

Eight identical concurrent cold-cache fixture requests caused eight upstream
requests. Locks protect dictionary access but do not share an in-flight fetch.
There are also separate date caches for discovery and result settlement.

The next-fixture endpoint can scan 21 dates from the UI, or 31 through the API.
With a 15-second timeout for each call, the request can wait minutes. Frontend
fetches have no overall timeout; switching leagues discards stale responses but
does not stop their backend scan.

Change: share in-flight calls per cache key, reuse provider date reads across
features, cap cache growth, set an overall request budget, and expose request/quota
telemetry. Your 1,000/day plan can serve small cached local usage, but current
limits do not guarantee that it will support arbitrary repeated multiuser scans.

### 7. Medium: there is no general regression CI gate

Sources: `.github/workflows/`, `web/tests/live.test.mjs`.

The only committed workflow is results refresh; it runs ingestion tests, not the
whole application suite on pushes/PRs. The frontend's ten tests cover helpers,
storage and probability handling, not mounted React flows. There is no committed
browser test suite. The previous busy-fixture ribbon overflow is an example of a
layout defect that helper tests and a build cannot catch.

Change: add push/PR checks for Python tests, agreed lint scope, frontend tests,
build and lint. Add a small browser suite for crowded matchdays, long club names,
date/league switches, failed providers and retries, stale responses, odds,
journal settlement, mobile navigation, and Safari/WebKit layout where practical.
Use provider fixtures in CI; keep authenticated checks explicit and quota-bounded.

### 8. Medium: displayed odds freshness is misleading

Sources: `market_odds.py::get_match_odds`, dashboard market note.

The provider returns the current server time as `fetched_at`, even when it reuses
the ten-minute event cache. It does not retain bookmaker `last_update` timestamps.
A controlled event with a bookmaker timestamp of October 13 was displayed with an
October 14 fetch timestamp. The UI calls that time “updated”.

The prices shown are inverse fair consensus probabilities, not necessarily prices
available from a bookmaker. A probability difference is a disagreement with that
consensus, not proof of positive expected betting return.

Change: retain cache-fetch time, quote-update times, bookmaker/source details and
the comparison timestamp. Label fair consensus prices explicitly. If actionable
value is a future goal, separately retain actual offered odds and evaluate against
those prices at the forecast's real decision time.

### 9. Medium: evaluation/research needs tighter reproducibility

Sources: `models.py`, `market.py`, `experiments/`, benchmark documents.

Outer season folds train before test dates, and the feature mutation passed. Inner
`TimeSeriesSplit` cuts rows rather than unique dates, however. All three cuts on
the current full Premier League fit straddled the same calendar date; other leagues
had examples too. This violates the strict same-date rule inside tuning/calibration.
It does not establish future-season leakage in the outer test.

The DC experiment fits team effects once before an entire season, while the
baseline's Elo/form features update through that season. Its unseen-opponent
indexing also defaults to the first training club before partially overriding
goal rates. These code paths deserve correction before treating the tested DC
implementation as the architecture's best possible result.

Some documented temperature-calibration, scoreline-evaluation and blending results
have no complete corresponding committed runner. Research scripts contain most
of the 52 full-repository lint errors and rely on positional season slices/private
helpers. Current benchmark pages contain literal `\n` sequences within tables.

Change: use date-grouped inner folds, the serving model's state/prior logic, a shared
explicit refit cadence, neutral regularised unseen-team parameters, and a single
runner producing machine-readable metrics, confidence intervals and tables with
data/code hashes. Keep already-inspected seasons as development evidence.

### 10. Medium/low: health and error handling are incomplete

Sources: `api.py`, `live_fixtures.py`, `market.py`.

- `/health` returned 200 with a missing history file, while `/teams` returned 400.
  This is a liveness check, not model readiness. Initial lazy fitting also adds
  about 15 seconds to the first catalogue/forecast request on this host.
- An API-Football JSON list raised an uncaught `AttributeError` rather than the
  advertised provider error. Unexpected JSON shapes can become HTTP 500 errors.
- The historical odds loader accepted infinity as a price and emitted a zero
  home probability. The manual/live prediction odds validator is stricter.
- A missing JavaScript asset returned the dashboard HTML with HTTP 200. Unknown
  API-like paths also fall through to the SPA, obscuring routing failures.

Change: add readiness/status with per-league cutoffs and engine state; validate
provider payload shapes and finite prices; return proper missing-asset/API errors.
Before public hosting, add quota protection for unauthenticated provider-backed
endpoints. A distributed cache or account system is not required for the current
single-user local setup.

## Frontend and maintainability assessment

The main experience retains fixture dates, hypothetical matchups, seven leagues,
favourites, odds comparison, actual model context, scorelines, journal and themes.
The demo remains isolated and the classic dashboard remains accessible. Team badge
fallbacks prefer provider images, then exact league-scoped static images, then
initials. There are 30 packaged crests for 128 current catalogue clubs; complete
logo availability therefore depends on provider images. No new visual crest audit
was performed in this review.

Strengths include stale-response guards, shared frontend reads, pre-kickoff saving,
legacy journal migration, and preservation of original probabilities during odds
comparison and settlement. The ribbon containment fix is present in reviewed main.

`Dashboard.tsx` is now 2,559 lines. Several large render functions, request state,
storage, export, selection and settlement live together. Split these into focused
hooks/components after behavior tests exist. Keep the approved design intact while
making behavior easier to verify.

“My teams” only shows followed fixtures in the loaded league and matchday. It is
not a global multi-league upcoming-favourites feed; the empty-state wording makes
that limitation explicit. Journal and favourites are browser-local and do not sync
to a phone, another browser, or a changed hostname. Export is currently the backup.
Accounts/NBA can remain later work.

Documentation also needs reconciliation: README should clarify its distinction
between unbundled raw source files and the bundled derived canonical CC0 dataset;
the package description mentions only two leagues; some older research snapshots correctly
refer to smaller datasets but should be prominently marked as snapshots. Generate
current coverage/metric tables from results rather than manually updating numbers.

results-based model rather than fabricating approximations. No need to revive xG
as an immediate dependency after the user's decision to skip it.

My preferred next action is **Checkpoint 1**, followed by **Checkpoint 2**. These
make existing forecasts more trustworthy without assuming a replacement algorithm
will outperform the current one.
